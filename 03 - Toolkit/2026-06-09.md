## TL;DR naming standards checklist

Use this as the **quick normalization pass** for the query.

# 1) GUID rule

**If a token ends in `GUID`, insert `_guid` and lowercase it.**

### Pattern

- `locGUID` → `loc_guid`
- `apptGUID` → `appt_guid`
- `patGUID` → `pat_guid`
- `persGUID` → `pers_guid`
- `apptstGUID` → `apptst_guid`
- `appttypGUID` → `appttyp_guid`
- `schdvwGUID` → `schdvw_guid`
- `ashGUID` → `ash_guid`
- `empGUID` → `emp_guid`
- `vendGUID` → `vend_guid`


### Rule

<anything>GUID  =>  <anything>_guid

---

# 2) Source system ID rule

Always split as:

- `source_system_id`

### Normalize

- `SourceSystemId` → `source_system_id`
- never `sourcesystemid`
- never `sourceSystemId`

---

# 3) Source system name rule

Use a separate text/code field:

- `src_sys` **or**
- `source_system_name`

### Recommendation

If you want full clarity / canonical naming, prefer:

- `source_system_name`

If you are keeping abbreviated warehouse-style names, then:

- `src_sys`

Just be consistent.

---

# 4) Snake case only

All column names should be:

- lowercase
- underscore-delimited
- no camelCase
- no PascalCase
- no embedded acronym casing

### Normalize examples

- `ashDateTime` → `ash_datetime`
- `apptDateTime` → `appt_datetime`
- `apptMinutes` → `appt_minutes`
- `persFirstName` → `person_first_name` _(or `pers_first_name` if preserving source prefix)_
- `persLastName` → `person_last_name`
- `vendUserName` → `vendor_user_name` _(preferred)_ or `vend_user_name` _(if preserving source token)_
- `locTimeZone` → `location_timezone`
- `apptstCode` → `apptst_code`
- `appttypCode` → `appttyp_code`

---

# 5) Separate words, not compressed compounds

If the name is made of multiple words, split them.

### Normalize

- `locationtimezone` → `location_timezone`
- `patientid` → `patient_id`
- `sortorder` → `sort_order`

### Your example

- `source_system_id` ✅
- not `sourceSystemId`
- not `sourcesystemid`

---

# 6) Preserve stable business abbreviations only if truly canonical

If an abbreviation is enterprise-standard and unavoidable, keep it. Otherwise expand it.

### Usually acceptable

- `appt`
- `pat`
- `emp`
- `vend`
- `loc`
- `src`

### Better for gold/semantic layers

Prefer expanded names where practical:

- `appointment_guid` instead of `appt_guid`
- `patient_guid` instead of `pat_guid`
- `location_guid` instead of `loc_guid`
- `vendor_user_name` instead of `vnd_user_name`

### Heuristic

- **bronze**: source-faithful abbreviations are okay
- **silver/gold**: expand where possible for semantic clarity

---

# 7) Don’t mix source-native tokens and semantic names in the same layer

Pick one style per layer.

### Bronze

Can preserve source-ish tokens:

- `appt_guid`
- `apptst_guid`
- `appttyp_guid`

### Gold

Prefer semantic names:

- `appointment_guid`
- `appointment_status_guid`
- `appointment_type_guid`

---

# 8) Use `_id`, `_guid`, `_sk`, `_nk` by meaning

Suffixes should be deterministic.

## `_guid`

Use for raw UUID/GUID identifiers

- `appt_guid`
- `loc_guid`

## `_id`

Use for business/natural/system identifiers that are not GUIDs

- `patient_id`
- `location_id`
- `source_system_id`

## `_sk`

Use for surrogate keys only

- `patient_sk`
- `location_sk`
- `appointment_type_sk`

## `_nk`

Use for natural keys only where that distinction matters explicitly

- `patient_id_nk`
- `location_id_nk`

---

# 9) Booleans must read like booleans

Use:

- `is_`
- `has_`
- `can_`
- `was_`

### Good

- `is_npe`
- `is_net_new`
- `is_pre_conversion`
- `has_previous_npe_same_window`

### Avoid

- `same_day_cancel_flag` ← better as `is_same_day_canceled` or `has_same_day_cancel`

---

# 10) Date vs datetime must be explicit in the name

If it is a date, end in `_date`.  
If it is timestamp/datetime, end in `_datetime` or `_ts`.

### Good

- `appt_added_date`
- `appt_datetime`
- `ash_datetime`
- `crt_ts`
- `upd_ts`

### Avoid ambiguity

- `created`
- `updated`
- `date_added`

---

# 11) Timestamps: use one convention consistently

Do not mix these casually:

- `_datetime`
- `_ts`

### Recommendation

- business event timestamps → `_datetime`
- technical audit timestamps → `_ts`

### Example

- `appt_datetime`
- `ash_datetime`
- `crt_ts`
- `upd_ts`

That split is good.

---

# 12) Status/type code vs description/name must be explicit

Use:

- `_code`
- `_name`
- `_description`
- `_desc` only if abbreviation is already standard in your environment

### Good

- `appt_status_code`
- `appt_status_name`
- `appt_status_description`

### Less ideal

- `apptttyp_desc` → better `appointment_type_description` or at least `appt_type_desc`

---

# 13) Avoid typo-like near-duplicates

Your query has inconsistent variants that should be normalized.

### Example issue

- `apptttyp_guid`
- `appttyp_guid`

Pick **one**.

### Recommendation

If preserving source token:

- `appttyp_guid`
- `appttyp_code`

If moving toward semantic clarity:

- `appointment_type_guid`
- `appointment_type_code`

But do **not** use both `apptttyp` and `appttyp`.

---

# 14) Avoid cryptic prefixes in curated layers

These are okay in bronze/source-faithful staging, but not ideal in curated semantic models:

- `ash`
- `apptst`
- `appttyp`
- `schdvw`
- `pers`

### Better semantic expansions

- `appointment_status_history`
- `appointment_status`
- `appointment_type`
- `schedule_view`
- `person`

# 15) Table names and column names should use the same lexical standard

If the table is:

- `#bronze_appointment_status_history`

then columns inside should prefer:

- `appointment_status_history_guid` **or**
- at least consistent short forms like `ash_guid`

Not a random mixture of:

- `ash_guid`
- `apptGUID`
- `SourceSystemId`
