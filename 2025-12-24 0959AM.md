## Powershell Learning

| $_           | automatic variable "current object in the pipeline"                                                       |
| ------------ | --------------------------------------------------------------------------------------------------------- |
| -LiteralPath | parameter passed to get path exactly as typed <br>no wildcard expansion or interpretation of special char |
When you use a pipeline (`|`), PowerShell sends objects down the pipe **one at a time**, and inside the next command—often inside `ForEach-Object`, `Where-Object`, `Measure-Object`, etc.—`$_` refers to **whichever object is being processed right now**.

## -LiteralPath
Many file/folder names can contain characters that PowerShell normally treats specially:

- `*` and `?` → wildcards
- `[` `]` → character sets
- `:` `\` `/` → separators  
    If you use **`-Path`**, PowerShell may try to interpret those. With **`-LiteralPath`**, PowerShell **does not** interpret; it uses the literal string.

You’re looking at a **PowerShell function parameter block**. It defines what inputs the function accepts and adds validation/behavior. Let’s break down each piece in plain English and then show a couple of usage examples.

---

## The code
```powershell

param(
    [Parameter(Mandatory = $false)]
    [ValidateScript({ Test-Path $_ -PathType Container })]
    [string]$Path = '.',
  
    [switch]$IncludeSystemFiles,
    [switch]$Delete,
    [switch]$Force
)
```
---

## What each part means

### `param ( ... )`

- Declares the **parameters** that a script or function accepts.
- This block must appear at the **top** of the script or inside a function, before any executable statements.

### `[Parameter(Mandatory = $false)]`

- Uses the **`[Parameter()]` attribute** to control metadata/behavior of a parameter.
- `Mandatory = $false` means the parameter is **optional**. If it were `true`, PowerShell would prompt the user to provide it (unless a default is supplied).

> You can add other `Parameter` properties here too (e.g., `Position`, `ValueFromPipeline`, `HelpMessage`).

### `[ValidateScript({ Test-Path $_ -PathType Container })]`

- A **validation attribute** that runs the enclosed script block to **approve/reject the incoming value**.
- `$_` represents the proposed value (the thing the user typed).
- `Test-Path $_ -PathType Container` returns **`True`** only if the path exists **and** is a **directory** (a “container”).
- If validation fails, PowerShell throws a **terminating error** before your function runs.

> Common alternatives are `[ValidateSet('A','B')]`, `[ValidateRange(1,10)]`, etc.

### `[string]$Path = '.'`

- The parameter’s **type** is `string`.
- The variable name is `$Path`.
- The **default value** is `'.'`, which means **current directory**.
- Combined with the validator, it ensures `$Path` is an **existing folder** (unless user overrides and fails validation).

### `[switch]$IncludeSystemFiles`, `[switch]$Delete`, `[switch]$Force`

- These are **switch parameters** (boolean flags).
- Switches don’t take a value; you either **include** them (they become `$true`) or **omit** them (`$false`).
    - Example: `-Delete` sets `$Delete` to `$true`.
- Typical use:
    - `IncludeSystemFiles` — “also include files marked as system/hidden.”
    - `Delete` — “perform deletion” (as opposed to dry-run).
    - `Force` — “be aggressive / bypass normal restrictions,” often passed to cmdlets like `Remove-Item -Force`.

> Important: Your custom `-Force` has **no effect by itself**; you must use it inside your code to modify behavior (e.g., pass `-Force` to underlying cmdlets, skip prompts, include hidden files, etc.).

## How this would sit inside a function

function Clean-Temp {

    [CmdletBinding(SupportsShouldProcess)]

    param(

        [Parameter(Mandatory = $false)]

        [ValidateScript({ Test-Path $_ -PathType Container })]

        [string]$Path = '.',

  

        [switch]$IncludeSystemFiles,

        [switch]$Delete,

        [switch]$Force

    )

  

    # Optional: expand path

    $Path = (Resolve-Path -LiteralPath $Path).Path

  

    # Example: decide which attributes to include

    $getChildParams = @{

        Path    = $Path

        Recurse = $true

        File    = $true

    }

  

    if ($IncludeSystemFiles) { $getChildParams['Force'] = $true }  # includes hidden/system

  

    $items = Get-ChildItem @getChildParams

  

    # Preview vs. delete behavior, honoring ShouldProcess / WhatIf

    foreach ($i in $items) {

        if ($Delete) {

            if ($PSCmdlet.ShouldProcess($i.FullName, 'Remove-Item')) {

                Remove-Item -LiteralPath $i.FullName -Force:$Force

            }

        }

        else {

            Write-Host "Would delete: $($i.FullName)"

        }

    }

}

### Notes

- `[CmdletBinding(SupportsShouldProcess)]` enables **`-WhatIf`/`-Confirm`** automatically for your function—very useful when the `-Delete` switch exists.
- `-Force:$Force` passes `-Force` to `Remove-Item` **only if** your custom `$Force` switch was used.

---

## How you’d call it

- **Default (current folder), just list what would be deleted (no actual delete):** Clean-Temp
    
- **Include hidden/system files in the scan:** Clean-Temp -IncludeSystemFiles
    
- **Actually delete (with safety preview):** Clean-Temp -Delete -WhatIf
    
    > Because of `SupportsShouldProcess`, `-WhatIf` prints what would be removed without deleting.
    
- **Actually delete, no preview, include system files, force underlying cmdlets:** Clean-Temp -Delete -IncludeSystemFiles -Force

## Quick mental model

- **`param`**: defines what inputs your function/script accepts.
- **`[Parameter(...)]`**: tweaks how PowerShell binds that input (mandatory, pipeline, position, etc.).
- **`[ValidateScript({...})]`**: lets you enforce rules _before_ runtime (e.g., “must be an existing folder”).
- **Typed parameter (`[string]`) + default (`=`)**: sets type & fallback value.
- **`[switch]`**: on/off flags—great for options like “include hidden,” “delete,” “force.”
