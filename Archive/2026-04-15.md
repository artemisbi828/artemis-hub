# 2026-04-15 Mental Model 1-Pager: Data Platform Tooling + Boundaries

## TL;DR
This is a **multi-concept model** (not single-concept).

You are managing one operating system of ideas with six tool concepts:
- Git (code/control plane)
- Azure (cloud/network/runtime plane)
- Terraform (desired-state infra plane)
- SQLMesh (transformation orchestration plane)
- Snowflake (data compute/storage plane)
- Atlan (metadata/governance/discovery plane)

The cleanest mental model is:
1. **Control what should exist** (Git + Terraform)
2. **Host where it runs** (Azure + Snowflake)
3. **Transform data reliably** (SQLMesh)
4. **Govern and discover meaning/access** (Atlan)

If boundaries blur, defects follow (security leakage, drift, ownership confusion, lineage gaps).

---

## ELI5 (Executive + New-Joiner Friendly)
Think of a modern hospital campus:
- **Git** = the approved policy binder (what rules/code are allowed)
- **Terraform** = the construction blueprint robot (builds what policy says)
- **Azure** = land, roads, gates, and utilities
- **Snowflake** = the clinical lab where data is processed
- **SQLMesh** = the lab workflow scheduler and SOP checker
- **Atlan** = the accreditation + catalog office (who can see what, meaning, lineage)

Each has a job. Trouble starts when one tool tries to do another tool’s job.

## Clinical Definitions (High-Fidelity, Concise)

| Term | Definition 1 | Definition 2 | Definition 3 |
|---|---|---|---|
| Git Monorepo | One repository for many services/modules with shared standards. | Enables atomic cross-component changes and centralized governance. | Increases CI scope unless pipelines are path-aware. |
| Git Polyrepo | Separate repositories per bounded component/domain. | Optimizes team autonomy and release isolation. | Introduces cross-repo coordination overhead for shared contracts. |
| Azure Resource Manager (ARM) | Azure control-plane API for provisioning/managing resources. | Declarative endpoint for create/update/delete of resources. | Source of truth for actual cloud resource state. |
| Terraform (on Azure) | Desired-state tool that plans/applies through ARM providers. | Reconciles state drift between config and live resources. | Works normally with ARM; ARM is the expected target, not a blocker. |
| SQLMesh | SQL-native transformation framework with environment-aware planning. | Adds dependency graphing, incremental logic, and safe promotion flows. | Governs data model lifecycle between dev/test/prod schemas. |
| Snowflake | Cloud data platform for compute/storage separation and secure sharing. | Executes warehouse workloads for analytics pipelines. | Access/network posture can be public or private (via approved controls). |
| Atlan | Active metadata and governance platform across data assets/tools. | Centralizes glossary, lineage, ownership, policy, and discovery. | Effective access depends on identity + network + source-system prerequisites. |
| Private Endpoint/Private Link | Private network path to services without traversing public internet. | Reduces exposure surface and improves compliance posture. | Requires VNet/DNS/routing design before app-level access succeeds. |

## Mono-Hierarchical vs Poly-Hierarchical Patterns

| Pattern | Looks Like | Use When | Risk |
|---|---|---|---|
| Mono-hierarchical | One top-down ownership chain | Tight governance, smaller team | Bottlenecks, slower change |
| Poly-hierarchical | Multiple bounded ownership hierarchies (platform/data product/security) | Larger org, domain autonomy | Interface ambiguity if contracts are weak |

Recommended here: **Poly-hierarchical with explicit contracts**
- Platform engineering: Azure + Terraform + base Git standards
- Data engineering: SQLMesh + Snowflake model lifecycle
- Governance: Atlan stewardship + policy workflow

## Focus Area 1: Monorepo vs Polyrepo (Acid Tests)

| Acid Test | If YES | If NO |
|---|---|---|
| Do you need frequent atomic changes across infra + transforms + governance configs? | Monorepo bias | Polyrepo acceptable |
| Are teams independently releasing with minimal shared code? | Polyrepo bias | Monorepo efficient |
| Is shared CI/CD becoming too expensive/noisy? | Polyrepo or path-filtered monorepo | Keep monorepo |

Decision shorthand:
- Choose **monorepo** when change coupling is high.
- Choose **polyrepo** when team autonomy and release isolation dominate.

## Focus Area 2: ARM + Terraform Compatibility

```text
Terraform config --> Terraform plan/apply --> AzureRM provider --> ARM API --> Azure resources
```

Key mental anchor:
- Terraform on Azure is not “despite ARM”; it is **because ARM is the control plane**.
- “No problem” condition depends on:
  - Correct provider auth/permissions
  - Clean state management and locking
  - Deterministic module/version strategy

Acid tests:
- If portal/manual changes occur, does plan show drift immediately?
- If state backend is unavailable, can apply still proceed safely? (should be no)

## Focus Area 3: Atlan Access Precursors

### Precursor Ladder (must be true in order)

```text
1) Identity/Authn/Authz ready
2) Network path allowed (public or private)
3) Endpoint/DNS resolution correct
4) Snowflake role/warehouse privileges correct
5) Atlan connector policy/scope validated
```

### Private vs Public Connectivity to Snowflake

| Option | Security Posture | Operational Complexity | Typical Fit |
|---|---|---|---|
| Public endpoint | Lower isolation, internet-routed | Lower | Fast start, non-restricted environments |
| Private Link / private endpoint | Higher isolation, private routing | Higher (DNS/VNet/routing) | Regulated workloads, strict governance |

### Azure VNet Considerations
- VNet/subnet boundaries must align with private endpoint strategy.
- NSGs/route tables/DNS are as critical as connector credentials.
- “Container exists” is insufficient; path + policy + name resolution must align.

Acid tests:
- Can Atlan resolve and reach Snowflake endpoint without internet egress?
- If public access is disabled, does lineage ingestion still pass?

## Focus Area 4: Infra Directory on Azure (Repository Convention)

Suggested top-level layout:

```text
/infra          # Terraform modules, env stacks, shared policy-as-code
/intra          # Internal platform contracts/runbooks/interfaces between teams
/extra          # External integrations, partner/system boundary artifacts
/sqlmesh        # Transformation projects/macros/environments
/governance     # Atlan policy mappings, glossary workflows, ownership matrices
```

Directory intent:
- **infra**: what is provisioned
- **intra**: how internal actors coordinate
- **extra**: what crosses enterprise boundary

---

## Infra vs Intra vs Extra (Boundary Taxonomy)

| Layer | Primary Question | Example | Anti-Pattern |
|---|---|---|---|
| Infra | “What must exist technically?” | VNets, private endpoints, Terraform modules | Mixing business glossary docs into infra state code |
| Intra | “How do internal teams operate together?” | SLA contracts, model ownership matrix, promotion runbooks | Treating team agreements as deployable infra resources |
| Extra | “What crosses outside boundary?” | Vendor integrations, external data sharing controls | External dependency logic hidden inside internal-only docs |

## Lifecycle Stages (End-to-End)

```text
Design -> Version (Git) -> Provision (Terraform/Azure) -> Connect (Network/Endpoint) ->
Transform (SQLMesh/Snowflake) -> Govern (Atlan) -> Monitor/Refine
```

Ownership checkpoint per stage must be explicit to avoid “everyone thought someone else owned it.”

## Application Examples (Max 3)

### Example 1: New Data Source Onboarding
1. Define source contract (intra).
2. Provision connectivity/secrets/endpoints (infra).
3. Build SQLMesh incremental models in Snowflake.
4. Register lineage/glossary/owners in Atlan.

### Example 2: Tight Compliance Environment
1. Enforce private endpoints only.
2. Disable public Snowflake access.
3. Validate Atlan connector via private routing + controlled roles.

### Example 3: Team Scale-Out
1. Keep shared platform in monorepo root standards.
2. Move domain pipelines to polyrepo as release autonomy grows.
3. Preserve contract files and lineage obligations centrally.

## Fast Decision Card

| Decision | Prefer A When | Prefer B When |
|---|---|---|
| Monorepo vs Polyrepo | Cross-domain atomic changes are frequent | Team/domain release independence is primary |
| Public vs Private endpoint | Speed and low setup burden dominate | Compliance and network isolation dominate |
| Central vs Federated governance | Vocabulary/risk profile is uniform | Domain semantics vary but need shared standards |
