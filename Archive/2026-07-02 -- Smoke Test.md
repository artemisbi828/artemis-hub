# What is pre-commit?

Think:

```text
Git Hooks Manager
```

Before code is committed it may run:

```text
Format Python
Lint Python
Check YAML
Check SQL
Detect secrets
Validate JSON
```

So:

```text
git commit
    ↓
pre-commit
    ↓
all validation rules
```

Many companies use this so bad code is blocked before reaching CI.

# What is a Python virtual environment (venv)?

Without a venv:

```text
Machine
 ├─ Python A
 ├─ Python B
 ├─ Package X v1
 └─ Package X v2
```

Things get messy.

A venv creates:

```text
Project
 └─ .venv
      ├─ python.exe
      ├─ pre-commit
      ├─ ruff
      └─ dependencies
```

Everything needed for that project is isolated.

Think:

```text
Mini Python installation
just for this repo
```

# What is the "uv trampoline issue"?

Ignore the fancy words and think:

A trampoline is an extra bounce.

Instead of:

```text
PowerShell
  ↓
pre-commit
```

you have:

```text
PowerShell
  ↓
wrapper
  ↓
uv
  ↓
wrapper
  ↓
Python
  ↓
pre-commit
```

One of those jumps is failing.

The agent suspects the executable launcher generated by `uv`.

***

# What is uv?

`uv` is a modern Python package manager.

Comparable to:

```text
npm (JavaScript)
nuget (.NET)
pip (older Python)
uv (newer Python tooling)
```

It often creates small launcher executables.

Example:

```text
pre-commit.exe
ruff.exe
pytest.exe
```

Those launch the real Python code behind the scenes.

***

# Why would calling pre-commit directly fail?

When you type:

```powershell
pre-commit run
```

you're usually not executing Python directly.

You're executing a launcher:

```text
pre-commit.exe
```

which then finds:

```text
python.exe
```

which then loads:

```text
pre_commit package
```

If any path is wrong:

```text
launcher broken
launcher stale
venv moved
python upgraded
```

then:

```text
pre-commit run
```

fails even though the actual package is fine.

***

# What does "call pre-commit via the venv Python module path" mean?

Instead of:

```powershell
pre-commit run
```

they want:

```powershell
.venv\Scripts\python.exe -m pre_commit run
```

Notice the difference.

### Old

```text
PowerShell
  ↓
pre-commit.exe
  ↓
Python
```

### New

```text
PowerShell
  ↓
python.exe
  ↓
pre_commit module
```

One less moving part.

Much more deterministic.

***

# Why do engineers prefer the second approach?

Because it answers:

> Which Python are we using?

Exactly.

Instead of:

```text
whatever Python happens to be on PATH
```

you get:

```text
THIS Python
inside THIS venv
inside THIS repo
```

which improves reliability.

# What you should update in your mental model

```text
PowerShell Script
    ↓
Activates project environment
    ↓
Uses project Python
    ↓
Runs pre-commit
    ↓
pre-commit runs quality checks
```

Key insight:

> `pre-commit` is not the check itself. It is an orchestrator that launches other checks.

And:

> Running `python -m pre_commit` is often more reliable than running `pre-commit.exe` because it bypasses launcher/path issues and guarantees the repo's virtual environment is being used.
