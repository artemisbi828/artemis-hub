1. Use **YAML** as source-of-truth for humans (easy to edit/review in PRs).
2. Compile YAML to **JSON** at runtime for strict validation.
3. Persist run results in **Parquet** (best for scale and analytics).
4. If you want one format only: use JSON with a JSON Schema.

**High-level data model for manifest**

1. `source_table` (snowflake schema.table)
2. `target_table` (azd schema.table)
3. `business_keys` (array)
4. `watermark/filter`
5. `column_mapping` (optional)
6. `sampling_order_by` (for deterministic sample rows)
7. `enabled` flag

**Approach vectors to consider**

1. **Python + Snowflake connector + pyodbc + DuckDB (recommended now)**:

- Fastest to implement.
- Great control over profiling, extraction, and diff logic.
- Easy to batch and rerun.

2. **SQLMesh-driven generation layer**:

- Use SQLMesh/macros to template extract and diff SQL per manifest entry.
- Good when you want governance, versioning, and reusable SQL artifacts.

3. **Orchestrated pipeline (Prefect/Dagster/Airflow)**:

- Best when this becomes scheduled/productionized.
- Adds retries, observability, lineage, and alerts.

**How to get your exact target output**

1. For each table pair, compute:

- `azd_row_count`, `snowflake_row_count`
- key-only-in-azd count
- key-only-in-snowflake count

2. Materialize sample rows:

- 3-5 rows only-in-azd
- 3-5 rows only-in-snowflake
- deterministic ordering by business key

3. Write final report table:

- `table_name | azd_row_count | snowflake_row_count | sample_only_in_azd | sample_only_in_snowflake`

**Opinionated recommendation for you**

1. Start with the Python + DuckDB pipeline now.
2. Keep manifest in YAML.
3. Store all run outputs in Parquet + one CSV summary.
4. Add SQLMesh only after the first successful end-to-end run.
